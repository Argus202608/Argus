# 第 5 章 · 贯穿全局的工程经验

> "一个多模态 Agent 能不能用，一半取决于模型多聪明，另一半取决于那些没人愿意讲的工程细节。"

前四章讲的是"看、听、想、说"四个能力层。但一个真实跑在用户面前的系统，还有一整层东西不属于任何单���能力——它们决定的不是"聪不聪明"，而是"卡不卡、乱不乱、能不能测、好不好配"。这些经验往往是踩了坑、熬了夜才换来的，却最少被写进文档。

这一章，把 Argus 开发过程中反复出现、反复被咬的几类工程问题集中讲清楚。它们背后有一条共同的线索：**实时多模态系统里，任何"每次都做一遍全量工作"的地方，都会在长会话下变成灾难。**

## 5.1 长会话性能：一切 O(N) 都会杀死你

多模态会话动辄几百上千轮。在这个尺度下，任何随轮数线性增长的操作都是定时炸弹。Argus 在三个地方被这条规律咬过。

### 坑一：主 Agent 流式硬卡死

现象：屏幕共享 + 多轮之后，主 Agent 的流式输出突然硬卡死，token 半天吐不出一个。

根因不在模型，在**线程**。大帧的 `json.loads`（一次 200KB+）跑在 WebSocket 的事件循环线程上，把负责下发 SSE token 的那个 loop 活活饿死。画面帧越大、越频繁，token 下发就越卡。

修复是把大 payload（帧、音频）的**解析和 dispatch 一起挪出事件循环线程**（`asyncio.to_thread`）：

```
_parse_and_dispatch:  大 payload 解析 + dispatch → 都 to_thread，别占着 loop
```

这个教训在本书里出现了不止一次——第 1 章帧采集"不做完整解码"、第 2 章 ASR final "扔到专用线程跑"，都是同一条铁律：**永远不要在事件循环线程上干重活。** 一个 loop 要同时喂 token、收帧、跑 TTS，任何一个环节贪心地占用它，其他环节就全饿死。

### 坑二：desktop 400 轮后卡顿

现象：桌面端聊到 400 多轮就明显卡。

根因藏得更深：incremental runtime 的名字叫"增量"，实际却在**每次流式 flush 时重放全部 N 条消息**——O(N) per flush，一轮 flush 几十次，就是 O(N²) 级别的浪费。

修复是让 `_syncMemo` 按 `ThreadMessage` 的身份**只同步真正变化的那几条**，删除扫描也用 orderKey 门控。名副其实的"增量"，才不会被历史长度拖垮。

### 坑三：屏幕共享卡 + 打字不流畅

现象：一边共享屏幕一边聊天，整个页面卡、打字不跟手。

根因是一个非常隐蔽的 React 陷阱：页面顶部的 header effect 依赖了 `frameCount`。帧每秒来两次，`frameCount` 每秒变两次，于是 `setAfterTitle` 每秒触发两次**整个 App 级别的重渲染**。你以为在共享画面，其实每秒在把整个页面重画两遍。

修复：把 `frameCount` 从 header 解耦 + 节流到 1/s。

> **这三个坑的共同教训：** 实时流会以每秒数次的频率触发某个操作。如果那个操作的成本是 O(N)（N=历史长度）或牵连了大范围重渲染，它在短会话里毫无征兆，在长会话里必然爆炸。**设计任何"每帧/每 flush 都做"的逻辑时，先问一句：它的成本会不会随会话变长而增长？**

### 前端渲染的另一类卡：Markdown 全量重解析

还有一类"卡死"根本不是后端的锅。比如某个工具输出一个大表格后页面"卡死"——F12 一看，后端在正常发 delta，是**前端每收到一个 delta 就把整段 Markdown 全量重新解析**卡住了主线程。没有视频流也一样卡。

终极解法是把巨型单组件拆成按列 memo 的子组件（`LeftPanels` / `ChatColumn` / `DeepColumn`），任何一处 setState 只重渲染它所在的那一列。**诊断"卡死"时，先分清是后端没发、还是前端没画——它们的药方完全相反。**

## 5.2 前后端状态一致性：一个会话，两处真相

多模态页有大量状态既存在后端（session 字典里的标志位）、又映射到前端（React atom）。这种"双份真相"是 bug 的温床。Argus 踩过一整类这样的坑。

典型场景：app 或网页关闭后，monitor / 深研作业的进程内对象其实已经死了，但历史记录里还显示 "running"。用户重开一��，一堆"运行中"的作业，其实全是僵尸。

修复是一套"重开即对账"的机制：重开时把这些残留作业标记为 **interrupted**、重新登记为 disabled，并给面板加上 on/off 开关。想重新启用？得先有视频流，否则开关自动弹回 off（走守卫 op）。**状态不是写一次就完了——进程重启、连接重连、会话切换，每个边界都要重新对账一次。**

还有会话切换时的串流 bug（`?mm=` 切换清理不全、事件不按 session 过滤）、`$mmSessionId` 与 `$activeSessionId` 的镜像同步……这些都指向同一个原则：**live 状态（进程内正在跑的）和 persisted 状态（存下来的）是两回事，混淆它们必然出 bug。** 一个作业"存着说它在跑"不代表"它真的在跑"。

## 5.3 会话模型漂移：resume 是一片雷区

一个特别阴险的坑：老会话（比如当初用 Kimi 建的）在你把 config 改成别的模型后，重新打开时行为诡异——有的报 400、有的凭空冒出个从没配过的模型、有的又完全正常。

根因是 resume 时用了**旧的 model + 新的 endpoint**（`billing_provider` 是 custom 时没被还原）。三种结果，取决于同步发生在会话状态的哪个时机。

修复是每轮做一次 `_sync_agent_model_with_config`：检测到 config 变了就自动切换，并在历史里写一条 "active model changed" 的 marker，让用户看得见。

这个坑还有一个副产品教训：**端点返回码本身不稳、不可当证据。** 同一个错误配置，这次 400、下次可能正常，取决于负载和缓存。排查时如果把"这次返回 400"当成确定信号，会被带进沟里。要看的是配置本身，不是某一次的返回码。

## 5.4 配置架构：唯一真相源

多模态子系统有一堆角色（主 Agent、monitor、watcher、memory writer/reviewer、recall、语音的 ASR/TTS……），每个都可能要独立配模型和端点。如果配置散落各处，很快就没人搞得清"这个角色到底用的哪个模型"。

Argus 的答案是**单一真相源**：项目根目录的 `config.yaml`（git 跟踪），dashboard 启动时单向复制到 `HERMES_HOME`。每个子模块的模型用一致的四元组 `{provider, base_url, api_key, model}`，`base_url` 留空就跟随主 Agent。

这里有两个值得学的约束：

1. **一致的四元组契约**：monitor / watcher / memory / recall 全用同一套 `build_submodule_client` 装配。新增一个角色，照抄这四件套就行，不用发明新格式。
2. **硬性前置显式报错**：记忆模型的 `vision_ability` 必须为 true，配错了启动直接崩、不静默降级（第 3 章讲过）。`hermes doctor` 还会校验"某视觉必需角色配了纯文本模型"并警告。**配置错误应该在启动时响亮地失败，而不是在运行时悄悄产生垃圾输出。**

## 5.5 评测：与线上完全一致的离线流水线

一个记忆系统好不好，得能测。Argus 的记忆评测（`mm-memory-eval`）有一个关键原则：**走与在线完全一致的多模态记忆流水线**——离线读一个视频，用和线上一模一样的 Writer/Reviewer 建记忆，再逐条 QA 经召回作答。不是另写一套简化逻辑，而是复用真实路径。只有这样，评测分数才真的代表线上表现。

它还支持**时序评测**：QA 可带提问时间点，视频喂帧推进到那一刻，就用**截至此刻的记忆现状**回答——逼真还原"看到该时间点时系统知道什么"。这正是第 3 章那条 `ask_ts` 防脏读铁律的用武之地。

评测框架本身也有工程细节：批跑要支持顺序执行、失败重试、断点续跑（一次跑几十个视频，中间挂了不能从头来）。这些都是"让评测真的能大规模跑起来"的必要条件。

第 3 章讲的空图 400 bug，正是在批量评测时才暴露的——**规模本身就是一种测试**。小样本下偶发、无害的问题，在大规模跑批���会稳定复现、暴露真因。

## 5.6 一以贯之的几条原则

回看全书，Argus 的设计里反复出现同几条原则。把它们抽出来，就是这套系统的"设计品味"：

1. **一份感知，多方消费。** FrameBuffer、MemoryStore 是所有模块的共享地基。公共决策（去重、场景判定）只做一次，全链受益。

2. **永远不要在事件循环线程上干重活。** 帧解码、ASR turn、大 payload 解析——全挪到线程池。一个 loop 喂 token、收帧、跑 TTS，谁贪心谁就把别人饿死。

3. **副作用汇流到唯一出口。** 出声收敛到 `_flush_to_tts`，把"该不该做"的判断收在一处。多一个旁路，多一个漏判。

4. **尽力而为、优雅降级、永不阻塞采集。** 场景模型挂了保持阈值、ASR key 没配就静默禁用、summary 超时用累积报告兜底——绝不因为一个非核心环节失败而拖垮主链路。

5. **无状态才能并发安全。** ToolBox 的 anchor 显式传参而非存实例，是并发正确的前提。

6. **让语义相近但角色不同的东西保持分离。** 三层记忆分层、快照双字段、live 与 persisted 状态、闲聊 QA 与主 history——揉成一坨省事，拆开才好用、才不出错。

7. **稳定与易变分离，缓存才命中。** 系统提示的稳定 tier 永不 per-turn 重渲染；主 Agent 不被动收帧，易变的提问时刻像素只进入 `query_multimodal` 接管后的 QueryWorker 任务，路由规则留在稳定 prompt 里。

8. **让错误早暴露、响亮地失败。** vision_ability 配错就崩、模型漂移写 marker、空图在发送前过滤——不要让错误伪装成正常，一路溜到最难排查的地方才炸。

9. **规模是一种测试。** 长会话暴露 O(N)，批量评测暴露空图 400。很多 bug 只在尺度上来后才现形——所以要主动在大尺度下验证。

## 尾声

从"打字问答"到"边看边聊"，Argus 想证明的是：一个 AI 助手可以不只是一个更聪明的对话框，而是一个真正"在场"的存在——它看着你的屏幕、听着你的话、记着你们一起经历过的事、在你需要时开口，也在你不需要时安静。

做到这一点，靠的不是某一个惊艳的模型或算法，而是四个能力层的协同，和这一章里那些不起眼却决定成败的工程决策。**眼睛、耳朵、大脑、嘴——外加一副能扛住真实世界的骨架。** 这就是让一个 Agent "活"起来的全部。
